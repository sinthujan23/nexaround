# NexAround AI Experience Discovery Changelog & Documentation

This file documents all architecture, endpoint definitions, caching mechanisms, and design implementations related to AI-powered experience discovery features in NexAround. Maintaining documentation here reduces token usage by preventing analysis of the main project README.

---

## 🗺️ AI Experience Discovery Carousel

The homepage dashboard features a horizontal discovery carousel displaying local events, activities, and hidden gems recommended by the **NexAround AI Discovery Engine** (powered by Gemini).

### 🚀 Performance & Backend Caching
To reduce Gemini API spend, avoid Google Places API quota consumption, and guarantee load times under **100ms** for end users, the discovery logic is fully managed on the backend:

1. **Endpoint:** `GET /api/v1/places/trending`
   * **Parameters:**
     * `district` (String): The district name (e.g. `Colombo District` or `Kandy District`).
     * `lat` (Float): Current latitude.
     * `lng` (Float): Current longitude.
   * **Returns:**
     * `markdown` (String): Raw markdown generated by Gemini listing events and gems.
     * `places` (List): Real Google Places records (rating, reviews, photos) matched to the AI experiences.

2. **Redis Cache-First Strategy:**
   * **Cache Key:** Built based on the normalized district name (e.g. `trending:v1:district:colombo_district`). If the district name is missing or generic, snaps coordinates to a `0.1°` grid (approx 11km) (e.g. `trending:v1:grid:6.90:79.80`).
   * **TTL:** **24 hours** (86400 seconds). Popular events and local hidden gems do not fluctuate on a minute-by-minute basis.
   * **Shared Cache:** Any user opening the app in the same district/coordinates grid will retrieve the cached data instantly from Redis, eliminating slow Gemini generations.

3. **Backend Resolution Pipeline:**
   * On cache miss, the backend invokes Gemini with a multi-model fallback chain (`gemini-2.5-flash` -> `gemini-2.5-flash-lite` -> `gemini-flash-latest` -> `gemini-2.5-pro`) to ensure high response rate.
   * Extracted place names from the markdown are matched in parallel against Google Places text search (using the cached `/places/search` service).

## 🎨 Mobile Client Card Fallback Design

Mobile clients fetch the discovery payload through a single HTTP GET request. The client maps the raw `_aiExperiences` to the carousel:

* **Resolved Cards:** If an experience matches a resolved place returned by the backend, it renders a card containing real Google Place images, star ratings, review counts, and exact distance badges.
* **Unresolved Fallback Cards:** If an experience cannot be resolved to a Google Place (e.g., street food crawl, temporary festival, beach walk), it is **never hidden**. The app renders a premium visual card containing:
  * A custom gradient background (`AppColors.primary` & `AppColors.surfaceVariant`).
  * A translucent central category icon (`Experiences` or `Attractions`).
  * An **AI Pick Match Score** badge (derived from Gemini confidence rating).
  * A structured timing badge showing date/hours.
  * Interaction: Tapping either resolved or unresolved cards triggers the same structured AI Experience Details bottom sheet modal.
